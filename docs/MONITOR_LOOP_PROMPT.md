# R51 コンパクト監視ループ

`/loop 3m` または同等の反復指示へ、次だけを貼る。詳細契約は別ファイルへ集約した。

```text
MNQ Nightwatchを1周期だけ実行。`python nqx_cycle.py`を1回だけ実行し、その最終行を返す。
BLOCKED/HALTなら最重要理由を1行だけ足す。取得・整形・publish・AUTO判定はこのコマンドの中で
完結しているので、MCPでの手動取得、rawの書き写し、個別stageの手動実行、生bundleの直接publish、
注文コマンドの直叩きはしない。値を手で再計算・転記しない。
```

## なぜここまで短いか（R51）

R44 版の指示文は、取得順序（左15m→due HTF→左15m復元→右3m→右下CVD/SMT→event）を
エージェントへ指示していた。**取得そのものがエージェントの仕事だったから**である。
R51 でそれを `tv_fetch.py` へ移した（`nqx_cycle.py` が毎サイクル最初に呼ぶ）ので、
指示文に取得手順を書く理由が消えた。

転記時代の実害:

| | 転記あり（〜R50） | `tv_fetch.py`（R51） |
|---|---|---|
| 取得 | 数分（bars3m 240本＋bars15m 60本の逐語出力） | **3.5 秒** |
| 1 周（publish まで） | 約 20 分 | **36 秒** |
| 必須8 raw の鮮度窓 240 秒 | 割る。`required raw acquisition is not fresh` が連続 | 余裕で収まる |
| 3分間隔 | 守れない（サイクルが重なる） | 守れる |

順序・pane・鮮度・足の幅の検証はすべて `tv_fetch.py` と `tv_snapshot.py` の中にある。
**指示文へ手順を書き戻さないこと** —— R39 で「段階を指示文に並べない」と決めたのと
同じ理由で、書いた手順は守られず、守られたかどうかも確認できない。

## 補足

- 受信箱は無期限停止中。呼ばず、その状態を BLOCKED/HALT の理由にもしない。
- CVD が `refreshRequired` のとき、`nqx_cycle.py` が次の一手を1行で出す。
- 監視窓（JST 07:00〜翌05:45。2026-09-05 に 04:00 → 05:45 へ延長）の判定は `nqx_cycle.py` が内部で行う。窓の外は1行だけ出る。
- 取得だけ手で確認したいときは `python tv_fetch.py`（publish しない）。
- **R84 追撃の影運転（2026-09-12〜）**: 建玉があって管理が何もしない周期に
  `pyramid: …` の注記が出る。`pyramid: ADD … [dryRun: not sent]` は「送るならこの枚数」
  の判定で、**一枚も送っていない**。`pyramid: <理由>` は見送りの機械的理由
  (`SIDE_MISMATCH` / `GRADE_BELOW_MIN` / `NO_ROOM` / `RISK_CAP_EXCEEDED` など)。
  `pyramid guard: … failed` が出たら実装の例外を握った印なので、その行をそのまま報告する。
  指示文は変えない —— 追撃も `nqx_cycle.py` の中で完結している。
