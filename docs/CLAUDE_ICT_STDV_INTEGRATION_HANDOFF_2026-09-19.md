# Claudeへの実装依頼 — ICT STDVと参加判断の接続

作成: 2026-09-19 JST。希望期限: 月曜2026-09-21の市場再開まで。

## 0. 依頼の目的と完了地点

ユーザーの目的は、Nightwatchが相場を読んでも参加できない問題を改善すること。ICT STDVを使い、**方向の仮説・押し目を待つ条件・残りの値幅・参加可能な位置**を別々に評価できるようにする。

資料を読んで説明するだけで終わらず、アンカー抽出、固定投影、既存評価への接続、再生比較、本番が読む設定の確認まで完成させてほしい。土曜の監視・発注・速度測定用注文は起動しない。AUTOの変更はこの依頼に含めない。

既存の実行契約・権限境界を守る。初期実装は設定でOFF、SHADOWで因果比較し、実際の新規候補へ効かせるLIVEとの違いを明示する。**SHADOW導入を「戦略改善が本番で有効」と報告しない。** LIVEの受け入れ条件に届かない場合も、独立して完成可能な実装・配線・試験・導入準備まで終え、未達を測定値で限定する。

## 1. 最初に読むもの

1. `TRADING_CONTEXT.md`、現行 `execution_contract.json`、`CLAUDE.md`、担当環境の `AGENTS.md`。
2. `docs/reports/ICT_STDV_SOURCE_AND_CODE_AUDIT_2026-09-19.md`。一次資料、動画の参照時刻、式、既存コードとの差分をまとめてある。
3. R119のLIMIT距離/TP1通過ゲート、現行stopLogic、既存 `fibSd` と方向票、目標選択、凍結プランの経路。

古い報告のSL上限・口座数・モデル成績を定数として転記しない。R119の逐次再生はBASE/BOTHとも+4.80Rと報告されており、R119で報酬改善済みとは扱わない。今回の比較には実際の現行設定を固定して用いる。

## 2. 先に固める採用仕様

出典の規則と、Nightwatch用に決めた規則を列で分けた仕様表を作る。特に、manipulationレッグの起点、掃引対象、CISD/MSSの確定条件、使用時間足、失効条件をコードと対応させる。

最小のv1は、既存の確定済みsweep→構造変化チェーンが十分な証拠を持つ候補にSTDVを付ける。モデル名だけで全BREAKER/TURTLE等へ適用しない。新しい独立エントリーモデルの追加は今回の必須要件ではない。

データに合わせて3分足を使うなら「TTradesの考え方を3分足へ適用したNightwatch版」と明記する。動画の2分足例を完全再現したとは書かない。既存足を合成して不足する時間足や隠れたスイングを捏造しない。

## 3. アンカーと投影の契約

名前案は `ictStdv` / `NQX_ICT_STDV/1`。既存の `fibSd` との互換を検査して確定する。

最低限、次を保持する。単なるhigh/lowペアでは足りない。

| 区分 | 必須情報 |
|---|---|
| 識別 | schema、anchorId、version、symbol/限月、sessionId、sourceTf、sourceHash、evidenceRootId |
| 根拠 | 起点の足IDと価格p0、掃引極値の足IDと価格p1、liquidityId、sweepAt、confirmation種別と足ID |
| 可知時刻 | 起点時刻、極値時刻に加え `confirmedAt` / `knownAt`。後から分かったスイングを過去へ戻さない |
| 投影 | 確定時のBUY/SELL、係数、生価格、tick丸め価格、幅、丸め規則 |
| 状態 | projectionValid、invalidReasons、lifecycle、lastObservedAt、各水準の到達時刻 |
| 関係 | 親/子アンカーID、関連decision/plan ID。方向の異なるアンカーを暗黙に上書きしない |

計算は `p(r)=p0+r*(p1-p0)`。BUYはp0が高値・p1が安値、SELLはp0が安値・p1が高値。出典資料の合成例を固定試験にする。

アンカー確定後、現値がEQを通っても方向・p0・p1は変えない。別の掃引を認定するなら別anchorIdにする。未来に良く伸びたアンカーへ差し替えない。再起動・再生でも同じ履歴から同じIDと水準を作る。

右側の足を使うpivotは、右側が閉じた時刻をknownAtにする。価格の時刻と発見可能時刻を混同しない。新たに確認した時点ですでに通過していた目標は、後から「事前予測成功」に計上しない。

`projectionValid` と `eligibleForDirectionVote` は別。新しい目標用STDVは `targetOnly=true`、方向票は0とする。既存ライフサイクルの `valid=false` に巻き込まれて目標消費者まで使えなくならないよう、型を分ける。

## 4. 「読む」と「参加する」を分ける

最低限、候補ごとに次を説明できる出力にする。フィールド名は提案であり既存スキーマに合わせてよい。

```text
thesis:        BUY / SELL / UNRESOLVED と、その否定条件
nearTerm:      直近の予測対象時間、予測方向、根拠。未検証の確率を付けない
participation: WAIT_FOR_PULLBACK / ENTRY_READY / NO_ROOM / INVALIDATED
entryZone:     待っている位置と、入るための既存トリガー
stdvContext:   固定アンカー、水準、消化済み目標、現在地
headroom:      現値→目標、予定Entry→目標、構造SLでのRをそれぞれ記録
invalidation:  何が起きれば今回のシナリオを撤回するか
```

BUY仮説と「短期に押す予測」は両立する。`WAIT_FOR_PULLBACK` は、今すぐ逆向きへ発注したり、無期限に指値で経路を占有したりする指示ではない。

STDV到達だけで新規逆張りを作らない。反対側へ参加するには、その方向の独立した構造証拠と既存ゲートが必要。上位足と下位足が食い違う場合は、それぞれの仮説・時間幅を出す。単に両方を同じ票数へ足さない。

到達済みかどうかは鮮度が確認できた価格/該当足で判定する。確定足の終値を当時の現値へ黙って代入しない。スイングの鮮度と現在価格の鮮度は別に検査する。

## 5. 既存取引への効かせ方

### 5.1 まず全消費者を追う

`strategy_models` → matrix票 → `msnr_gate`候補 → `target_pool/model_targets` → 最終decision → 凍結プランの経路を確認する。上流levels経由で既存fibSdが目標へ混入していないかも調べる。

既存fibSdを削る変更と、新STDVを足す変更は別に比較できるようにする。古い方向票の除去だけで改善した結果を、新STDVの目標精度改善と呼ばない。

### 5.2 比較する変更を絞る

初回は次の2段階を混ぜない。パラメータの総当たりは不要。

- **TARGETS:** 適格なアンカーの投影を目標候補として評価する。どの既存目標と比較し、何が選ばれたかを残す。
- **PARTICIPATION:** TARGETSとは別の設定で、到達済み目標や残り値幅を参加判断に使う。単に投影域へ触れたことをハードブロックにしない。

目標候補を `extra` に追加するだけで終えない。既存 `model_targets` は遠方の候補をrunnerへ選び得るため、`-4` を追加するだけでTPが不当に遠ざかる可能性を試験する。v1では `-4` は観測用を既定とし、runnerへの採用は独立した明示設定と比較結果を必要とする。これはNightwatch用の実装方針であり動画の規則ではない。

`-2/-2.5` の反応域、近いDOL/FVG、予定EntryとSLの位置を合わせて目標を選ぶ規則を先に固定する。STDV単独で遠いTPを正当化して最低Rを通す仕組みにしない。複数投影の重なりは位置の情報として扱い、同じ根拠を独立した加点として重複計上しない。

新STDVの欠損だけで、従来有効だった全モデルを停止しない。STDV必須として新たに作った候補は欠損時に不成立、従来候補は従来経路へ戻す。この違いをログに残す。

### 5.3 実行契約との接点

- Entry/SLの構造、枚数、口座別上限、R119、AUTO、所有権、発注前検査は維持する。STDVでSLを広げたり内側へ縮めたりしない。
- TP1/runnerの2本の独立OCOを維持する。投影目標が2本の有効な異なる価格にならない場合に、同じTPを複製して通さない。
- 新規候補のTPが変われば、現在の契約どおりdecisionId/凍結プランへ反映する。「価格を変えたがID不変」で過去claimを流用しない。
- 保有中の凍結済みTP/SLを、アンカー更新や `-4` 継続の解釈で変更しない。今回は新規プラン評価の統合に限定する。
- 未約定プランが目標消化済みでも、独自の口座全体flattenを追加しない。既存の所有権を検証した取消経路へ理由を渡す。

## 6. 必須の受け入れ試験

| 試験 | 合格条件 |
|---|---|
| BUY/SELL投影 | 資料の合成値と全係数で一致。符号逆転・1幅ずれなし |
| 半tick/重複/異常値 | 丸めが決定論的。ゼロ幅、NaN、無限値、不正価格は不適格。丸めで潰れたTPを2本扱いしない |
| 掃引だけ/戻りなし | 未確認アンカーから参加可能なSTDVを作らない |
| 未来参照 | 全足一括再生と逐次再生でknownAt以後の出力が一致。右側pivot確定前には出ない |
| EQ通過/再起動 | 確定アンカーの方向と価格が変化しない |
| 銘柄/限月/時間足 | 他限月・不足時間足・古い根拠を黙って流用しない |
| 現値と確定足終値 | 別々に扱い、価格代用の有無を集計する |
| 到達と再訪 | 消化済み水準を再訪しただけで未消化へ戻さない。反転の自動発注もない |
| 1本の足で複数事象 | 掃引・確定・Entry・SL/TPの前後が不明なら保守的判定/不明。都合のよい足内順序を仮定しない |
| 方向票 | 新STDVのtargetOnlyが0票。投影健全性は別フィールドで保持 |
| 旧経路と二重計上 | 旧fibSdと新STDV、親子アンカーの同一根拠を独立票へ増幅しない |
| 目標消費者 | 入力→候補→選択TP→最終decisionまで追跡できる。表示だけで終わらない |
| OFF/SHADOW | 基準の注文意図・Entry/SL/TP・decisionIdが不変。SHADOW監査情報の差だけ許可 |
| LIVE候補/保有管理 | 変更範囲は承認済みの新規候補。凍結済み建玉の管理は不変 |
| 実プロセス境界 | 保存JSONを実際の子プロセス相当で読み直して型、時刻、探索パス、設定版を確認。通信・発注は遮断 |
| 回帰 | 担当環境の許可された試験経路で実施。既存失敗と新規失敗を同条件のbaselineで区別 |

単体入力だけで「本番統合済み」と結論しない。一方、文書・可逆な表示変更に不要な巨大試験を増やさない。上表は戦略動作・状態・入出力の実質的な境界を検証するためのもの。

## 7. 再生比較で答えること

同じデータ、実際に効くriskCap/stopLogic、同じ約定規則・手数料・スリッページ、同じ逐次ポジション制約で比較する。台帳と凍結プランを扱う場合は担当環境の権限に従い、外部共有資料に秘密情報を出さない。

最低限、BASE / 新STDV SHADOW / TARGETSの3条件。PARTICIPATIONはTARGETSとの違いが解釈できてから。旧fibSd票を変えるなら、その単独条件も切り分ける。

報告する数値:

1. 適格アンカー件数、根拠欠損件数、確定までの遅延、確定時すでに目標消化済みの件数。
2. 目標投影が候補/最終decisionに実際に使われた件数、無効果だった理由。
3. 約定率、未約定のままTP1到達した件数、指値による経路占有時間。
4. 逐次の純損益/ΣR、最大DD、取引数、費用、MFE/MAE。並列に存在した全候補の損益合計で代用しない。
5. 方向予測の評価時間と方向精度、参加判断後の約定/損益を別集計。STDV水準到達率をエントリー勝率と呼ばない。
6. 学習/規則選定に使っていない後続期間での結果。標本が足りなければ不足と記載し、過去の選別済み数例をholdoutと呼ばない。

「目標を遠くすればRが増える」は計画上の値であり、期待報酬改善ではない。入力価格を代用したサンプルと実観測価格のサンプルを混ぜて結論しない。1件の大勝・大敗で符号が変わるなら、その依存性を示す。

LIVE昇格は、上記の正しさ・運用互換・比較の条件が揃い、ユーザーの変更承認範囲と現行運用契約に適合するときに行う。週末にオフラインの正しさを示すことと、実市場での期待値を立証することを分ける。未立証の利益を期限に合わせて保証しない。

## 8. 月曜までの進め方と最終報告

1. 現行コード・並行変更を確認し、仕様表と既存との差分を確定。
2. 状態と投影を純粋な計算として実装し、固定値・未来参照・再起動を検証。
3. 候補評価と目標選択へOFF/SHADOW/LIVEの区別を保って接続。
4. 同条件の逐次再生と回帰を完了。修正したら影響箇所を再検証。
5. 本番起動先が読むファイル・設定・コード版を、通信なしで確認。`C:\Users\exexu\Downloads\nq-nightwatch-claude-code-handoff` と古いworktreeを混同しない。
6. 担当変更だけをコミット可能な単位に整理し、他セッションのR118/Jev/データ研究の差分を混ぜない。監視は起動しない。

最終報告は、変更ファイル、採用したアンカー定義、実測した効果、モード、実際のconsumer、試験結果、未確認の市場条件、戻し方を含める。導入後に観測が必要な項目は具体的なログキーと期待値を示す。

「表示できた」「模擬で通った」「起動先に存在する」「本番判断が変わる」「期待値が改善した」を別々に報告する。完了した部分を曖昧に半分残さず、未達は理由と次に必要な最小の証拠まで特定してほしい。
