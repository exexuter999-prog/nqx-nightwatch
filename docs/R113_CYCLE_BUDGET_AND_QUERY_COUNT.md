# R113: 7 口座でサイクルが 3 分に収まらない —— 実測と、効かなかった対策

2026-09-19 未明。`broker_status.py` / `autotrade_engine.py`(deploy 不要)。

## 症状

* `monitor_publish.py` が **300 秒のタイムアウト**で落ち、そのサイクルは何も publish しない。
* 成行 ENTRY が `ENTRY_CLAIM_MARKET_PRICE_STALE` で必ず落ちる。
* `broker position is UNVERIFIED for <口座>` が頻発する。

## 実測(推測を置かないための数字)

`NQX_BROKER_PROFILE=1` で 1 サイクルの照会を全部記録した(`.secrets/broker_profile.jsonl`)。

| 種別 | 本数 | 秒 | 1 本 |
|---|---|---|---|
| orders | **98** | 159.1 | 1.62 |
| positions | 23 | 65.1 | 2.83 |
| balance | 14 | 34.0 | 2.43 |
| position | 22 | 21.0 | 0.95 |
| fills | 1 | 4.4 | 4.44 |
| roster | 2 | 0.5 | 0.23 |
| **合計** | **160** | **284.0** | |

段階別では TradingView 取得が 5.2 秒、**publish 段が 132〜284 秒**。つまり時間はほぼ全部
ブローカー照会で、**口座あたり 23 本**という本数そのものが原因。

### 成行が通らない理由

`marketOrder.maxPriceAgeSec = 60` 秒。実測で **取得から 137 秒**かかっており、CONSUME の
時点で参照価格が必ず 60 秒を超える。1 口座のときは収まっていた門が、7 口座で構造的に
通らなくなった。**指値は通る。成行だけが落ちる。**

## 効かなかった対策(記録として残す)

### 並列化は速くならない

口座ごとの照会は独立なので、`broker_status.parallel_map()` を入れて
`query_balances` / `query_positions` / `query_orders_by_account` を並列にした。結果:

| 設定 | サイクル | 結果 |
|---|---|---|
| 逐次 | 300 秒超 | タイムアウト |
| 6 並列 | 132 秒 | **4 口座が UNVERIFIED** |
| 3 並列 | 180 秒 | **3 口座が UNVERIFIED** |

CrossTrade は同時接続を絞る。6 並列にすると 1 本の往復が **1.4 秒 → 4.2 秒**へ伸びて
相殺され、429 で落ちる本数だけが増えた。**速度は変わらず信頼性だけ下がる。**

仕組みは残してある(`NQX_BROKER_PARALLEL`、**既定 1 = 逐次**)。照会本数が減って
実際に 3 req/s へ近づいたら効くようになるので、そのときに上げて測り直す。

### R111 の retry と間引きは、この状況では逆効果

R111(2026-09-18)は「1 本の一過性 429 を吸収する」ために入れた。ところがレート制限は
**全部の照会に同時にかかる**ので、「たまたま落ちた 1 本」ではなく「全部落ちている」状態では
retry が待ち時間を積むだけになる。実測:

| | サイクル |
|---|---|
| R111 の間引き + retry あり | **300 秒超(タイムアウト)** |
| 間引き 0・retry 予算 0 | **198 秒** |

既定を安全側へ倒した:

* `HTTP_MIN_INTERVAL_SEC` **0(間引きなし)** —— 逐次で既に 0.7 req/s しか出ておらず
  発動しないのに、retry と重なって待ちだけ積む。
* `HTTP_RETRY_BUDGET_SEC` **5 秒**(プロセス全体)—— 一過性の 429 を 2〜3 本ぶん吸収して
  そこで諦める。使い切ったら以後は 1 回で `Unavailable`。
* 400 を retry しない規則(R53 の終端判定が依存)は不変。送信経路に retry を入れない規則も不変。

## いまの状態

サイクル **183 秒**。タイムアウトはしないが、**3 分の周期(180 秒)に収まっていない**し、
成行の 60 秒にはまったく届かない。

## 決定的な発見 —— CrossTrade は「遅延」で絞る

同じ照会を 5 回続けただけの実測(2026-09-19 03:05):

| 回 | 往復 |
|---|---|
| 1 | 0.69 秒 |
| 2 | 0.62 秒 |
| 3 | **5.05 秒** |
| 4 | **4.99 秒** |
| 5 | **16.26 秒** |

**429 を返すのではなく、応答そのものを遅らせる。** これで全部説明がつく:

* 並列にしても速くならない(サーバ側で待たされるので同時数は無関係)。
* retry も間引きも効かない(429 が出ないので retry は発動せず、間引きは
  「連続 2 本目まで」の閾値に対して粗すぎる)。
* **照会を増やすほど 1 本あたりが指数的に遅くなる。**本数がそのまま効く。
* 夜通し叩いた後ほど遅い。20:57 に 1 本 1.37 秒だったものが 03:00 には 3〜5 秒。

つまり打ち手は **照会本数を減らすこと以外に無い**。

## 効いた対策 —— 表示・会計の読み取りを共有する

呼び出し元を記録したところ、同じデータを別々の呼び出し元が取り直していた。
`broker_status.cached_read` / `query_balance_cached` / `query_position_cached` を足し、
**表示(`live_position_line`)と会計(`trade_journal.reconcile`)と ULTRA サイジング
(`build_accounts_payload`)だけ**を共有にした。

**安全条件(テスト `tests/test_r113_read_cache_safety.py` で固定):**

* 送信の前後で建玉/注文を確かめる経路(`autotrade_engine._scoped_position_query` /
  `_scoped_order_query` / `order.py`)は**共有を使わない**。生の `query_*` を呼ぶ。
* `order.py` を起動するたびに `invalidate_read_cache()` で必ず捨てる。
  **ドライランでも捨てる** —— 送ったかどうかを親は断定できない。
* 注文には共有版を作らない(`query_orders_cached` は存在しない)。注文照会は
  送信の検証そのもの。

TTL は 1 サイクルを丸ごと覆う 240 秒(`NQX_BROKER_READ_CACHE_SEC`)。25 秒にしていた
ときはサイクル 258 秒に対して短すぎ、engine が取った建玉が表示・会計の番までに
期限切れになって共有の意味が無かった。

結果: `trade_journal` が 20 本 107 秒 → **7 本 12.8 秒**、サイクル **258 秒 → 111 秒**。

| 周期 | 秒 |
|---|---|
| 03:06 | 111 |
| 03:09 | 125 |
| 03:13 | 216 |

**3 分(180 秒)に収まる周期と、収まらない周期がある。** ばらつきはこちらの都合ではなく
CrossTrade の絞り方による。成行の 60 秒にはどの周期も届かない(**指値は通る**)。

## 残っている本丸 —— 照会本数を減らす

`orders` が 98 本(口座あたり 14 本)なのが突出している。凍結注文 ID は 2 件しか無いので、
per-order 詳細ではなく **同じ一覧照会を 1 サイクルに何度も呼んでいる**のが疑い
(reconcile / recovery の stable double-read / `order.py` のドライランと送信前検査 /
trade_journal が、それぞれ独立に照会している)。

1 と 2 は済んだ(呼び出し元タグ + 表示・会計の共有)。残っているのは **engine の
送信検証経路**で、ここは共有できない:

    autotrade_engine._scoped_position_query   20 本  54.3 秒
    autotrade_engine._scoped_order_query      22 本  25.3 秒

`_reconcile_one` が **口座ごとに丸ごと 1 セットの照会**をするため、7 口座で 7 セットになる。
減らすなら「1 サイクルに 1 回だけブローカーの状態を取り、全部の消費者へ配る」設計へ
変えることになる(= R87 の「一括照会」)。**送信の検証そのものなので、設計変更は
建玉が無く相場が閉じているときに、テストを先に書いてから行う。**

それまでの現実的な選択肢は 3 つ:

1. **口座数を減らす。** 照会は口座数に比例し、遅延は本数に対して指数的に効く。
2. **指値だけで運用する。** 成行は取得から 60 秒の門に構造的に届かない。
3. **一括照会を実装する。** 本丸だが、送信経路の設計変更。

## 2026-09-19 03:15 — 実際に効いた軽量化

| 対策 | 前 | 後 |
|---|---|---|
| **fill_watch の恒常的な競合** | FLAT でも 14 秒ごとに 14 本 = **1 req/s を常時占有**(429 が 15 回) | `idleIntervalSec` 5 → **45 秒** = 0.31 req/s。**429 が 0 回**に。建玉があるときの 1.5 秒は変更なし(TP1 検知は無傷) |
| **残高の重複照会** | 28 本(口座あたり 4 本。`build_accounts_payload` が 1 サイクルに 3 回呼ばれる) | **7 本**。`nqx_state._cached_balances` の 30 秒キャッシュ(`NQX_BALANCE_TTL_SEC=0` で無効) |
| **孤児プロセス** | タイムアウトしたサイクルの `monitor_publish.py` が生き残り、次のサイクルと枠を奪い合う | 手で停止。**計測時にパイプで出力を絞ると親シェルだけ返って孤児が残る** —— サイクルはファイルへ落として測ること |

結果: **300 秒タイムアウト → 145 秒**(照会 70 本)。

**建玉と注文はキャッシュしない。** 「今 FLAT か」を決める安全ゲートなので、1 本たりとも
古い値を使わない(CLAUDE.md §6.1「建玉ゼロと推測しない」)。キャッシュしたのは残高だけで、
これは残機の表示と ULTRA の枚数計算に使う量。数秒の遅れが判定を変えることは無い。

## まだ残っている本丸 —— 建玉照会 32 本 / 79 秒

`positions`(複数形)16 本 56.4 秒 + `position`(単数形)16 本 22.9 秒 = **79.3 秒**。
7 口座に対して 4.6 本ずつある。内訳:

* engine の reconcile が 1 口座 1 回 → **単数 + 複数の 2 本**
  (R41: 単数が FLAT と言ったら複数形で裏取りする。2026-08-25 に単数形が FLAT と
  言っている裏で SHORT 2 枚が実在した。**この裏取りは外せない**)
* `_stable_broker_snapshot` の二重読み(before / after)→ さらに **4 本**

つまり **recovery が毎周期走っていることが 2/3 を作っている**。宙ぶらりんの claim ができる →
recovery が二重読み → 遅くなる → CONSUME が 60 秒を超えて期限切れ → また宙ぶらりん、という
循環になっている。R112 で claim は捨てられるようになったので、**サイクルが 60 秒を切れば
この循環は自然に切れる**。

次の一手は「recovery を毎周期走らせない」で、削減見込みは **−50 秒**。
