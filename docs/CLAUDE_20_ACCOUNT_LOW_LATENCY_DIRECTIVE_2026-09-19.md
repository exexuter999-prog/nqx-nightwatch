# Claudeへの実装指示：20口座を1口座に近い応答時間で運用する

私の目標は、20口座まで増やしても、シグナルへの反応、全口座への発注、TP1後の保護変更、取消・決済が口座数に比例して遅くならない運用です。7口座のサイクルが180秒以内になっただけでは完了ではありません。重複照会の削減から、観測・意思決定・送信・会計を分けた設計へ進めてください。

設計、隔離実装、テスト、性能検証、移行手順の作成まで進めてください。日常的な実装判断ごとに「続けますか」と止める必要はありません。性能値は実測・推定・目標を区別し、達成していないものを達成したと報告しないでください。

この指示は実装作業の依頼です。引用された過去の全決済依頼を再実行する指示ではありません。既存の運用権限と新規方式の本番導入を区別し、速度測定のために注文を作らないでください。

## 1. 現状を正しく引き継ぐ

最初にTRADING_CONTEXT.md、AGENTS.md、CLAUDE.md、execution_contract.json、適用される開発制約、作業ツリーの差分、docs/R113_CYCLE_BUDGET_AND_QUERY_COUNT.md、docs/R114_CYCLE_SNAPSHOT_MULTI_ACCOUNT.mdを確認してください。同時編集や監視の二重起動を避け、他の作業の差分を上書きしないこと。

2026-09-19にCodexがコードと文書を読んで確認した点：

- R114～R116の文書には7口座で47秒、57秒、40秒の記録があります。これは過去の記録であり、この指示作成時の再実測ではありません。会話の「145秒」だけを基準にしないでください。
- broker_status.prime_cycle_snapshotは口座ごとに建玉・注文・残高を順番に取得しています。名前が「一括」でも、全口座を一度の通信で取得する実装ではありません。
- 「3N本」は論理照会の数です。query_positionがFLAT時に複数形positionsで裏取りするので、通常のFLAT取得だけでも建玉2本＋注文1本＋残高1本で最大4N本になる経路があります。cache miss数をHTTP本数として報告しないでください。
- fill_watch.next_delayはmax(fastIntervalSec, sweep_cost / maxRequestsPerSec)です。現在の設定はfastIntervalSec=1.5、maxRequestsPerSec=1。20口座全部OPENなら次回までの待機だけで20秒になり、さらにobserveの巡回時間と管理時間が加わります。「1.5秒を変えていないからTP1検知は無傷」は成立しません。
- broker_status.cached_readには240秒TTLがあり、R113時点とR114以後の説明も混在しています。取得時刻、実際の消費経路、送信後の失効をコードで監査してください。TTL内であることは発注に使える証明ではありません。
- _stable_broker_snapshotにはbefore/orders/afterと最大3回の試行があります。復旧が繰り返される原因と、その実HTTP本数を分けて計測してください。

これらは改善箇所の入口です。行番号や既存コメントを無条件に正本とせず、着手時の実装を確認してください。

## 2. 最初に通信方式の前提を更新する

現在のexecution_contract.jsonには「TradovateはRESTのみ」とあります。しかし2026-09-19に閲覧した[CrossTrade公式WebSocket仕様](https://crosstrade.io/docs/api/websocket-api#tradovate-over-the-websocket)は、origin=tradovateによる注文・約定・建玉イベントを記載しています。価格データは別経路が必要です。

また[公式レート制限](https://crosstrade.io/docs/api/rate-limiting)ではRESTとWebSocket RPCは利用者単位の共通枠で、3リクエスト/秒、バースト20です。プッシュ受信はRPCの枠を消費しません。接続は利用者あたり1本です。

第一候補を「単一の常駐接続によるイベント受信＋状態集約」にしてください。WebSocketで同じ照会を20回送るだけの置換では不十分です。

現在の契約・接続先で利用できるか、全対象口座・複数のリンク先identityを覆うか、全体取得の範囲とページング、応答の完全性、送信経路の制限を確認してください。公式仕様で可能なことと、この環境で検証したことは分けて報告してください。新しい接続が既存接続を切断しないよう、接続所有者を確認してから運用者の権限内で試験すること。Codex/Devin等に委任する場合は、本番接続と秘密ファイル禁止の制約を引き継いでください。

仕様に関する根拠は上記公式資料を参照し、以降の設計・目標値はこのプロジェクトの要求として扱ってください。

## 3. 採用する構造

```text
ブローカーのイベント＋起動/欠落時の状態再取得
                ↓
常駐Broker Gateway（接続所有・検証・世代管理・通信予算）
                ↓
口座別の検証済み状態＋永続イベント記録
       ├─ 実行Coordinator → 既存の発注検証・送信経路
       ├─ TP1/runner/取消/決済の管理
       ├─ 戦略サイクル・Workerへの正本publish
       └─ 表示・会計・通知（実行の応答待ちから分離）
```

Gatewayがブローカー通信の調停を担い、各プロセスが独自に照会と再試行を積まない構造にしてください。表示・会計・監視は同じ検証済み観測を消費します。order.pyの安全判定は維持し、通信を委譲するなら同じ検証関数と監査を通してください。Gatewayから直接送信して既存ゲートを迂回する設計は禁止です。

口座数とともに増えるイベント量・ローカル計算・ブローカーの実処理は残ります。「O(1)」と呼べるのは接続数や定常時の戦略サイクルが追加する照会数などに限定してください。巡回を別プロセスへ移しただけで、裏の20口座分の遅延を解消したことにしないでください。

### A. 状態集約と整合性

- 状態鍵は環境・口座ID・契約IDを含める。銘柄名欠落をFLATと解釈しない。R41/R42の単数FLAT・一覧OPENの事故を回帰条件にする。
- R41の目的は偽のFLATを防ぐこと。旧経路の二重照会を先に削除せず、新経路の完全性と契約ID照合で同じ事故を検出できることを証明する。等価な証明ができなければ移行しない。
- snapshotId、接続session/epoch、口座別generation、scope、元データの観測時刻、受信時刻、整合性状態を保存する。ファイルを書き直した時刻で鮮度を更新しない。
- 初期取得とイベントの競合を処理する。購読中のイベントを取りこぼさず、重複・順序逆転・再接続・sequence欠落・resyncを扱う。順序や完全性を証明できない期間は未検証とする。
- heartbeatの健全性と個別データの更新時刻を分ける。単にイベントが来ないことをFLATの証明にせず、変化のない口座を毎秒全件照会する設計にも戻さない。
- 手動注文、取消、外部約定、口座消失、限月変更も世代更新に含める。ローカルorder.pyの呼び出しだけでキャッシュ失効を管理しない。
- TTLだけで発注を許可しない。送信直前に必要な証拠、期限、scope、世代、価格を確認する。HTTP再取得を減らすなら、代替証拠を契約とPython/Worker双方で明示してテストする。

### B. 送信と保護変更

- 戦略評価は共通で一度、口座別リスク・権限・残余枚数・注文所有権は口座ごとに確認する。全口座FLATを要求する現在の新規条件を勝手に変更しない。
- 重い取得・計算・表示を済ませてから期限付き実行権を取得する順序を検討する。CLAIM→CONSUME→送信の契約と凍結intentの同一性は保持する。
- 最初の口座を送った後、他の口座が共通キャッシュ全消去・全件再照会のために待つ構造をなくす。失効と再確認は必要な口座・状態に限定し、同一口座の操作は直列化する。
- 口座間はプロバイダー制約内で並行処理できるようにする。広域ロックをネットワーク待ちの間ずっと保持しない。世代比較、予約、fencing等で二重所有を防ぐ。
- 2枚をTP1とrunnerに分けるOCO契約を保持する。1口座の保護変更を、他19口座の照会、会計、UI更新で待たせない。
- 「HTTPを送った」「CrossTradeが受け付けた」「ブローカーが注文を受理した」「約定した」「保護注文が有効になった」を別状態として記録する。約定を待たない指値の受付遅延と、約定遅延を混同しない。
- 20口座のうち途中までしか送れなかったときの結果を口座・脚ごとに保持する。不明な送信は再送せず、未送信と混同しない。新規の継続可否は既存の部分成功/HALT契約を維持する。停止しても受理済み建玉の保護管理は継続する。
- SL/TP、枚数、許容価格乖離、現在の60秒価格鮮度条件を性能対策として緩めない。最新価格の取り直しがintentを変える場合、同じCLAIMへ値だけ差し替えない。

### C. 通信枠、復旧、会計

- REST/RPC、監視、送信前後照合、復旧を通した共通の通信予算を持つ。実際の発注Webhook等が別枠なら、確認した制限ごとに管理する。並列数だけ増やして解決したとしない。
- 優先順位は、既存建玉の緊急保護/取消/決済、TP1後管理、新規発注、整合性回復、表示・会計の順を基本とする。安全判定に必要な確認は、その操作の予算に含める。低優先処理の滞留にも上限を設ける。
- recoveryは未解決claim、接続欠落、クラッシュ復帰などの原因がある対象に限定する。毎周期全口座を復旧しない。ただし未解決状態を処理済みに偽装したり、期限切れだけで送信なしと断定したりしない。
- 安定二度読みが必要な旧復旧経路は別々の実観測で証明する。同一キャッシュを二度返して成功させない。
- fillsは約定イベント、未確定会計、再接続後の追補などに応じて取得する。FLAT継続でも前回観測の間に往復売買が完了し得るため、「qtyが変わらなかった」だけで履歴取得を永久停止しない。永続cursorと低頻度の照合を用意する。
- 表示用残高とリスク/サイジングに使う残高を区別する。後者の鮮度を「数秒なら影響なし」と仮定しない。
- heartbeatだけでなくプロセス所有と起動世代を管理する。タイムアウト時の子孫プロセス回収を含め、孤児の照会・送信継続と二重起動を防ぐ。生きたロックをstale扱いで削除しない。

## 4. 数字で合否を決める

次は保証値ではなく、まず目指す合格目標です。N=1/7/20を同じ条件で比較してください。

| 指標 | 目標 |
|---|---|
| イベント受信→ローカル状態反映 | p95 ≤100ms、p99 ≤250ms |
| 全条件が揃った実行可能判定→最初の送信開始 | p95 ≤1秒、20口座による増分 ≤250ms |
| 同判定→全対象口座のブローカー注文受理 | p95 ≤5秒、20口座時は1口座時＋2秒以内を目指す |
| TP1イベント受信→該当口座の保護変更送信開始 | p95 ≤1秒 |
| TP1発生→保護変更がブローカーで有効と確認 | p95 ≤3秒を目指す。上流時刻が無ければ測定不能部分を明記 |
| 新しい市場証拠の取得→戦略サイクル完了 | p95 ≤15秒、p99 ≤30秒を目指す |
| 定常・状態変化なしの戦略サイクルが追加する口座別ポーリング | 0。低頻度照合と障害時取得は別に計上 |
| 二重送信、偽FLAT、他口座ID混入、保護漏れ、期限切れ価格の送信 | 故障注入テストで0件 |

イベント受信後の速度だけ速くても、ブローカー→受信が遅ければ達成ではありません。ブローカー発生時刻、CrossTrade側の時刻、ローカル受信時刻を区別し、同期精度と欠測を併記してください。3分足の評価待ちは、この処理遅延と別に報告すること。戦略時間足の変更はこの依頼に含みません。

サイクル全体の秒数に加えて、各段階の待ち時間、送信キュー待ち、口座間の受理時刻差、状態鮮度の最悪値、実HTTP/RPC数、429、タイムアウト、復旧回数を記録してください。正常FLAT周期だけで合格にしないでください。

### 上流制約による下限を先に計算する

20口座×2脚が仮に40回の個別リクエストを必要とし、その送信が3 req/s・バースト20の同じ枠を使うなら、満杯からでも補充待ちの下限は(40−20)/3≒6.7秒です。応答時間と事前照会を除いても5秒目標は不可能です。これは条件付き算術であり、現在の発注ルートの実測値ではありません。

実ルートのリクエスト数、適用制限、バースト残量を確認して同じ計算をしてください。達成できない場合は、公式の複数口座ルーティング/サーバー側ミラー/一括送信の対応範囲、脚別OCO・口座別結果の取得可否を調べ、必要な経路変更・費用・最善の実測値を提示してください。全体が原子的に成功するとは仮定しないこと。観測だけ速くなった段階で「1口座と同じ瞬発力」と完了宣言しないでください。

## 5. 検証と導入

1. 現状の呼び出し関係と1/7/20口座の通信予算を作る。実測資料を使う場合は日時・コード版・周期種別を付ける。遅延をすべてプロバイダーの絞り込みと断定せず、内部待ち・HTTP・再試行を分ける。
2. Gateway、状態集約、実行Coordinatorの境界を短い設計書にし、通信/状態/時刻を注入できる形で実装する。新挙動は既定OFFまたはSHADOW。既存戦略ルールの変更を混ぜない。
3. 1/7/20口座で、通常FLAT、未約定、同時ENTRY、全口座同時TP1、部分約定、取消競合、手動注文、片脚拒否、1口座の遅延/消失、価格失効、429、イベント欠落/逆転/重複、再起動を試験する。
4. 送信前後のクラッシュも注入する。送信済み・未送信・結果不明が区別され、再起動で不明注文を再送しないこと、残る保護が追跡されることを確認する。
5. 隔離テストは現行の指定ランナーpython tests/run_all.pyと必要なWorkerテストを使い、外部到達0件・本番ファイル書き込み0件を固定する。性能ケースを指定ランナーへ組み込む。仮想時計による負荷試験と実時間の負荷試験は別表にする。
6. 各代表ケースで最低1000件の測定サンプルを得てp50/p95/p99/maxと失敗率を示す。失敗・期限切れを成功サンプルから黙って除かない。20口座での持続負荷試験を最低2時間行い、キュー蓄積とメモリ増大も検査する。外部へ1000件の実注文を送る意味ではない。
7. SHADOW比較で既存方式との差を説明する。実環境の7口座での確認と、20口座を模擬した結果は区別する。実口座が20個なければ20口座本番達成は未検証と明記する。
8. 起動停止、接続所有の移行、既存注文の引継ぎ、ロールバック、Worker変更時のdeployを含む手順まで作る。本番有効化の承認が未取得なら、具体的な差分・検証結果・戻し方を揃えた最後の段階でだけ確認する。

納品は、変更ファイル、採用構造、1/7/20口座の比較表、失敗試験結果、満たした目標/未達目標、その原因、導入と戻し方を簡潔にまとめてください。通信方式が未対応でも、隔離実装・性能下限・代替経路の調査など進められる作業を完了させてください。
