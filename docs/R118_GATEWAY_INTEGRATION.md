## 0. R117 の訂正 —— 「6.67 秒の下限」には根拠が無かった

R117 で「N=20 の『判定 → 全口座受理 p95 ≤5 秒』は**算術的に不可能**(下限 6.67 秒)」と
書いた。**この断定は取り下げる。** 根拠にしていたのは「40 本の送信が 3 req/s・バースト 20 の
枠を使う」という仮定だが、公式文書はそう言っていない。

2026-09-19 に `https://crosstrade.io/docs/api/rate-limiting` を読んで確認した:

> All API requests, whether over HTTP or WebSocket, share a single rate-limit budget of
> **3 requests per second**

* 対象として挙がっているのは **HTTP REST(`/v1/api/*`)と WebSocket RPC**
* バースト 20、購読は別枠(約 20/分・バースト 5)、**受信フレームは枠を消費しない**
* 超過は 429 + `Retry-After`、連続 10 回の違反で close 1008

**このページに `/v1/send/` は一度も出てこない。** 我々の発注はそこへ POST している
(`CROSSTRADE_URL` は `https://app.crosstrade.io/v1/send/…`)。確かめるには本番の注文を
作るしかないので、**こちらでは確認できない**。問い合わせ文は
`docs/R118_CROSSTRADE_INQUIRY.md`(**未送信**)。

代わりに、下限を**読みごとに分けて**出す。`execution_coordinator.floor_table()` がこれを返す。
本数は **模擬ブローカーで ENTRY の全経路を数えた実測**(§5):1 口座あたり
`/v1/api/*` **6 本**(FLAT 検証 2 + 送信前の窓 2 + 脚ごとの identity 2)と
`/v1/send/` **2 本**。

| N | REST・送信も予算内 | REST・送信は枠外 | **Gateway**・送信も予算内 | **Gateway**・送信は枠外 |
|---|---|---|---|---|
| 1 | 0.00 秒 | 0.00 秒 | 0.00 秒 | 0.00 秒 |
| 7 | 12.67 秒 | 8.00 秒 | **1.00 秒** | **0.00 秒** |
| 20 | **47.33 秒** | 34.00 秒 | **14.00 秒** | **0.67 秒** |

Gateway 列でも api が 0 にならないのは、**約定履歴の窓(`_fills_snapshot`)が REST に
残る**ため(1 口座 1 本)。`executionUpdate` の行を Gateway に持たせれば 0 本になり、
N=20 は 7.33 秒 / 0 秒まで下がる —— **そこは未実装**。

**api 6 本は最良の場合。** 注文行がすぐ現れない周期は identity 束縛が
`NQX_IDENTITY_SETTLE_ATTEMPTS`(既定 8)まで再照会するので、最悪 1 口座 20 本。
その読みでの下限は **N=7 で 45.3 秒 / N=20 で 140.7 秒**。

**この最悪値は実際に起きている。** 2026-09-19 22:42 に 7 口座の BREAKER SELL が
`ENTRY_CLAIM_MARKET_PRICE_STALE` で落ちた周期は、取得から 137 秒で 60 秒の門を
超えていた。上の最悪側(N=7 で 45.3 秒の補充待ち + 実リクエスト時間)と整合する。

**読み取れること:**

* 予算の問題は **送信ではなく検証**だった。N=20 の 47.3 秒のうち
  **34 秒は `/v1/api/*` の 120 本**(確実に枠の対象)で、Gateway が消せる部分。
* 5 秒目標に届くかどうかは **`/v1/send/` が枠の対象かどうかだけ**に懸かっている。
  枠外なら 0 秒、枠内なら 7.33 秒で **2.33 秒足りない**。
* いずれにせよ **今日の 47.3 秒よりは大幅に良くなる**。そこは確認待ちではない。

安全側の既定: `sendCountsAgainstApiBudget` は `null`(未確認)で、Coordinator は
**送信も枠を食う前提**で確保する。少なく確保して 429 を踏むより、多めに確保して少し
遅い方がまし。回答が来たら契約の 1 行を書き換えるだけで効く。

## 2. 採用した構造

### 2A. 出所層 —— 消費者は 1 行も変えない

既存の消費者(engine / 表示 / 会計 / ULTRA サイジング)は全部
`broker_status.query_position_cached` / `query_orders_cached` を通っていた。
その **1 段下**に `broker_source` を入れ、**同じ戻り値の形のまま出所だけ**を切り替える。

```
          消費者(無改造)
   engine / live_position_line / build_accounts_payload / trade_journal
                     │
        broker_status.query_*_cached      ← ここだけ 1 行差し替えた
                     │
              broker_source              OFF / SHADOW / LIVE
               ├── gateway-ws  ← .secrets/broker_gateway_snapshot.json(押し込み)
               └── crosstrade-rest ← 従来の HTTP
```

**1 回の操作は 1 つの出所で読む。** MODIFY の事前検査(建玉・保護注文の guard)と
identity 窓は同じ `_verify_*` を通る —— 片方が REST で片方が押し込みだと、1 回の
MODIFY が**別々の瞬間の見え方**で判断することになる(R78 の裸 runner guard は
「逆方向の生きた行が何本あるか」で分岐するので、ここがずれると危ない)。

**意図的に触っていない経路**(全部 REST のまま):

* **送信の「後」の再照会**(`order.py` の `middle` / `after`)—— 押し込みの
  スナップショットを読んでも「送った結果」の証明にならない(CLAUDE.md §4)。
  コードにもその旨を書いてある(後から親切で差し替えられないように)。
* **追撃(pyramid)の基礎建玉の確認** —— 影運転中で、ここは保守的に REST のまま。
* `broker_status.live_reads()` の中 —— 二度読みが証明になる経路(不在証明の三点読み、
  R52 の一瞬 FLAT 再確認)。同じスナップショットを二度読んでも証明にならない。
* 残高 —— WebSocket に残高は流れてこない。1 口座 1 本/サイクルのまま。
* `known_order_ids` 付きの注文照会 —— 特定 ID の終端状態は一覧では証明できない。
  「一覧に無い」と「ブローカーが解決できない」は意味が違う(R53)。

**FLAT を名乗る条件は REST より緩くしていない。** Gateway が持つのは
`Tv_ListPositions`(一覧)由来 —— 2026-08-25 に単数エンドポイントが取りこぼした側ではなく
**正本だった側**。さらに R41/R42 と同じ規律で、**別 `contractId` に非ゼロが 1 行でもある
口座は FLAT と言わず REST へ落ちる**。

整合性は口座ごとに見る。全体 VERIFIED でもその口座の行が落ちていれば使わない。
鮮度は契約 `brokerObservation.maxAgeSec`(30 秒)。**性能対策として緩めていない。**

### 2B. 実行 Coordinator

```
  Coordinator.run(op_key, accounts, build_args)
        │
        ├── AccountLane(A)  … 口座内は直列・プロセス横断のロック
        ├── AccountLane(B)  … 口座間は並行(maxParallel まで)
        │       │
        │   CommsBudget      … **ファイル越しに共有**(3 req/s・溜め 20)
        │       │
        │   runner(args, confirm) = order.py の subprocess(全ゲートを通る)
        │
        └── 併合: 口座 × 脚の envelope を 1 本へ(engine と台帳は無改造)
```

守っていること:

* **Gateway から直接送らない。** 送信は従来どおり `order.py` で、安全ゲート・
  分割 OCO・claim・台帳はそのまま。
* **結果不明は終端。** `UNKNOWN` のレーンを再送しない。同じ `opKey` + 口座は
  一度しか入れない(送る **前** に印を付けるので、途中で落ちても二度入らない)。
* **併合で行を落とさない。** envelope を読めなかったレーンは、その口座の両脚を
  `UNKNOWN` として残す。落とすと「送っていない」と読めてしまう。
* **rc=0 でも envelope が無ければ送信済みと言わない。**

**ENTRY だけはプロセスへ分けられない。** `order.py` は `consume_entry_claim` で
claim を 1 回消費し、その intent hash には `accountScope` が入る。口座ごとに
`--accounts <1 口座>` で呼ぶと intent hash が変わって `ENTRY_CLAIM_INTENT_MISMATCH` に
なり、そもそも 2 本目以降は claim が消費済みで通らない。よって **ENTRY の並行化は
`order.py` の中**(`post_split_to_accounts` のレーン)で行う。MODIFY / FLATTEN は
元々口座ごとなので Coordinator でプロセスを分けられる。

口座内は必ず直列。TP1 → RUNNER の**送信順**が脚 identity 束縛の根拠(R52/R76)なので、
ここを並べ替えると所有権が取れなくなる。

並行時の出力は口座ごとに溜めて入力順に出す。そのまま print すると行が混ざり、
`route_envelope` の「SNAPSHOT と FINAL は各 1 本」「途中に ERROR 印を出さない」という
契約を壊す。

### 2C. TP1 後の管理

`fill_watch` の**構造は変えていない**(観測 → 変化 → `trigger` → `reconcile`)。
変えたのは **観測の出所**と、そこから出る**見回り間隔**だけ。

```
next_delay = max(fastIntervalSec, sweep_cost / maxRequestsPerSec)
```

`sweep_cost` は「この見回りで打つ HTTP の本数」。押し込み由来の行は **0 本**として数える
(枠を消費しないので)。混在すれば REST の口座だけ数える。

| N | REST 由来の間隔 | Gateway 由来の間隔 |
|---|---|---|
| 1 | 1.5 秒 | **1.5 秒** |
| 7 | 7 秒 | **1.5 秒** |
| 20 | **20 秒** | **1.5 秒** |

指示 §1 が指摘した「20 口座で TP1 検知が 20 秒待ちになる」はこれで消える。
**他口座の照会・会計・通知を待たない** —— 見回りは 1 回のスナップショット読みで
全口座ぶんが揃い、変化した口座の `trigger` だけが走る。

**穴を空けないための退避**: Gateway が落ちている・鮮度切れ・その口座だけ RESYNCING、の
どれでも **その口座は REST へ落ちる**。全体が落ちれば全口座 REST(= 従来の挙動)。
`fill_watch` を先に止めることはしない —— 止めるのは Gateway が本番で回り切ってから。

### 2D. 読めない押し込みで整合性を落とす(新しい門)

**押し込みフレームの正確な形は実地未確認。** R117 の観測窓では建玉・注文の変化が
1 件も起きず、`status` と RPC 応答しか届かなかった。文書の形は
`{type, accountId, contractId, position:{…}}` だが、RPC 応答は本体を `data` で包む。

両方の形を読めるようにした上で、**知っている種類のイベントなのに口座や注文 ID を
取り出せなかったら整合性を落として全体再取得へ回す**(`unreadable_events` を数える)。

これが無いと最悪の事故になる: 押し込みの形がこちらの想定と違うと、イベントは
届いているのに 1 件も適用されず、**最後の全体取得の状態を「検証済み」と名乗り続ける**。
無言検知も発火しない(フレームは届いているので)。全口座が FLAT に見えたまま固まる。

| 所要 | **7.91 秒** | **1.92 秒** |

REST のまま。建玉と注文の照会は実質 0 秒になった。

再接続の最中に測った回は **10.20 秒 / Gateway 9 件 / REST 退避 5 件**
(`INTEGRITY_UNVERIFIED`)。**落ちている間はちゃんと REST へ落ちる** —— 穴は空かず、
そのぶん遅くなるだけ。これが設計どおりの degrade。

参考(R117、2026-09-19 深夜、建玉と 42 本の注文があった時間帯): REST 16.27 秒 /
実 HTTP 28 本、Gateway 1.16 秒 / RPC 4 本。**ブローカーの混み具合で REST 側は大きく
振れる**(7.91〜16.27 秒)。Gateway 側は振れない。

### 観測 1 回の所要(20 口座・模擬)

`fill_watch` は 1.5 秒ごとに全口座を見回る。その 1 回の所要:

| | 20 口座の観測 1 回 |
|---|---|
| 当初 | p50 **56.5ms** / p95 **74.9ms** |
| 契約・設定の写しを持った後 | p50 **17.1ms** / p95 **26.3ms** |

差の正体は **設定ファイルの読み直し**だった。`mode()` と `max_age_sec()` が
口座ごと・照会ごとに呼ばれるので、20 口座の 1 回の見回りで 20KB の JSON を
40 回以上 parse していた。mtime で写しを持つようにして 3.3 倍速くなった
(**運用中に契約を書き換えれば次の読みで効く**性質は保っている)。

1.5 秒間隔に対して 26ms なので、見回りの占有率は 2% 未満。

### 退避が集中したらどうなるか(指示 §5)

**時間ではなく本数で測る。** 所要はそのときのブローカーの混み具合で 2 倍以上振れる
(REST で 7.91 秒と 16.27 秒を同じ日に実測)が、本数は決定論的で、時間はその関数になる。

20 口座で、Gateway が答えられない口座を増やしていったときの照会本数(模擬):

| 退避した口座 | 建玉 REST | 注文 REST | 残高 REST | Gateway が答えた件数 |
|---|---|---|---|---|
| 0 | **0** | **0** | 20 | 40 |
| 1 | 1 | 1 | 20 | 38 |
| 5 | 5 | 5 | 20 | 30 |
| 10 | 10 | 10 | 20 | 20 |
| 20 | 20 | 20 | 20 | 0 |

**きれいに線形で、崖も増幅も無い。** 全口座が退避すると **従来の REST と同じ本数**
(40 本 + 残高 20 本)へ戻るだけで、それより悪くはならない。観測が止まることもない
(未検証の口座は 1 つも出ない)。

実際に再接続中の周期を実ブローカーで踏んだときは、7 口座中 5 口座が
`INTEGRITY_UNVERIFIED` で退避し、1.92 秒 → **10.20 秒**になった。これは上の表の
「退避 5」に対応する挙動で、**設計どおりの degrade**。

### 持続負荷試験が見つけた不具合 —— 全体取得が「足し込み」だった

**R117 の 88 件も R118 の単体試験も見逃していた。** 20 口座を回したときの
**メモリの伸びだけ**がこれを指していた。

`_apply_full`(`Tv_ListOrders` / `Tv_ListPositions` の結果を入れる関数)が、
既存の行を消さずに上書きマージしていた。消していたのは「一覧に 1 行も無かった口座」
だけで、**一覧に何かある口座ほど古い行が溜まる**という最悪の形。

一覧が返すのは「いま生きている全部」なので、切断・resync の最中に取り消された注文や
決済された建玉は **出てこない**。古い行が残ると:

* 取り消し済みの注文が `ordStatus: "Working"` のまま `liveOrders` に出続ける
  → **新規が blocking order で塞がる**
* さらに悪いことに、`verify_protective_orders` / `oco_sibling_pair`(R80)が
  **幻の保護脚**を数え、「runner は守られている」と誤答しうる ——
  **R78 の裸 runner の逆パターン**(守られていないのに守られていると信じる)
* 決済済みの建玉が残り、**存在しない建玉**を報告する

**記憶の問題ではなく正しさの問題だった。** 直して `4f. 全体取得は足し込みではなく置き換え`
(7 件)を追加 —— 一覧から消えた注文が消えること、消えた建玉が 0 枚になること、
20 回取得しても行数が増えないこと。Gateway の確保量は 0.25 → 0.14 MB。

**なぜ単体試験で出なかったか**: 試験が流していたのは「まっさらな状態への全体取得」か
「前回の上位集合」だけで、**行が減る取得**を一度も試していなかった。故障注入は
「壊れた入力」に寄っていて、「正常だが前回より少ない入力」が抜けていた。

### 実プロセスでしか出なかった不具合 2 件

手で組んだスナップショットの試験(72 件)は全部通っていたのに、**実際に
`broker_gateway --serve` を回して `prime_cycle_snapshot` から読んだ瞬間**に 2 件出た。
「統合が完了している」を実プロセスで確かめる意味がここにある。

1. **`writtenAt` が単調時計だった。** 書く側は `time.monotonic()`、読む側は
   `time.time()` と引き算。プロセスが違えば起点が違うので **常に `STALE`**、
   全口座 REST へ退避していた。壁時計で書くよう修正し、
   「**BrokerGateway 本体に書かせたファイルを出所層が受け取れるか**」を試験に固定した。
2. **口座名と `accountId` が繋がっていなかった。** REST は URL に**口座名**を使い
   (`/accounts/<名前>/position`)、WebSocket の行は **`accountId` しか持たない**。
   消費者は口座名で引くので、全部 `ACCOUNT_NOT_OBSERVED` で退避していた。
   `CROSSTRADE_ACCOUNT_ID_<名前>` を別名として繋ぎ、戻り値の `accountId` は
   **口座名**(REST と同じ)、`account` / `brokerAccountId` は**ブローカー側の値**に揃えた。

どちらも「模擬では名前と ID が同じ」「スナップショットを手で組んだ」ために
隠れていた。**単体試験が緑でも、統合したとは言えない。**

## 5. 送信側の実測(模擬ブローカー)

**往復時間を明示して測る。** 0ms は構造(本数と直列性)だけを見る値。並行化の効きは
往復時間に支配される。本番の CrossTrade は 1 本 0.6 秒前後(2026-09-19 実測)なので、
150ms は**控えめな**代用値。

| 往復 | N | レーン 1 | レーン 6 | HTTP | 内 送信 | 1 口座あたり |
|---|---|---|---|---|---|---|
| 0ms | 1 | 0.016 秒 | 0.000 秒 | 5 | 2 | 5.00 |
| 0ms | 7 | 0.094 秒 | 0.563 秒 | 35 | 14 | 5.00 |
| 0ms | 20 | 0.344 秒 | 0.578 秒 | 100 | 40 | 5.00 |
| **150ms** | 1 | 0.625 秒 | 0.625 秒 | 5 | 2 | 5.00 |
| **150ms** | 7 | 4.453 秒 | **1.281 秒** | 35 | 14 | 5.00 |
| **150ms** | 20 | 12.437 秒 | **2.516 秒** | 100 | 40 | 5.00 |

* **20 口座・往復 150ms: 逐次 12.44 秒 → 6 レーン 2.52 秒(4.9 倍)**
* **往復 0ms の行は構造(本数と直列性)だけを見た値で、検査にしていない。**
  待ち時間が無い測定はスケジューリングの雑音に支配され、同じ機械で他の試験が
  動いているだけで並行化が効いてしまう。「0ms では得が無い」も「得は往復時間とともに
  伸びる」も、**どちらも負荷次第で崩れた**(3 回中 1 回)。断定できるのは
  **往復 150ms 側の比(5.0 倍)だけ**で、そこだけを検査にしている。
  本番の往復は 0.6 秒前後なので、実運用の得はこの表より大きい。
* 送信本数は必ず 口座 × 2 脚。レーン数を増やしても増えない(= 二重送信していない)。
* 1 口座あたりの HTTP は口座数によらず 5 本(api 3 + send 2)。

**この表にレート制限は入っていない。** 模擬ブローカーは絞らない。本番では §0 の下限が
この上に乗る —— N=20 なら **47.3 秒**(今日)/ 14.0 秒(Gateway・送信も予算内)/
0.67 秒(Gateway・送信は枠外)。**実運用の値は「この表の値」と「下限」の大きい方**になる。

### 送信側で本当に効いているもの(**実測**)

ENTRY 1 回で `order.py` が打つ `/v1/api/*` を段階ごとに数えた(模擬・3 口座):

| 経路 | FLAT 検証 | 送信前の窓 | 送信ループ(identity) | 送信 | 照会 api | 1 口座 api |
|---|---|---|---|---|---|---|
| REST | 6 | 3 | 12 | 6 | **15** | **5.00** |
| Gateway(`sendVerification=true`) | **0** | **0** | 6 | 6 | **0** | **0.00** |

**全脚 ACCEPTED は変わらない** —— identity は押し込みから束縛できる。送信本数も同じ
(検証の出所を変えても送信は変わらない)。この表の `_fills_snapshot`(1 口座 1 本)は
含んでいない —— **約定履歴は Gateway に行として持っていない**ので REST のまま残る。
実運用では **api 6 → 1 本**になり、N=20 の下限は **47.3 → 14.0 秒**。
`executionUpdate` の行も持てば 0 本になり **7.33 秒**まで下がるが、そこは未実装。

`identity_probe` は 1 脚ごとに注文一覧を読み直す(`NQX_IDENTITY_SETTLE_ATTEMPTS` 既定 8 回 ×
`NQX_IDENTITY_SETTLE_DELAY_SEC` 既定 0.5 秒)。**行が出るまで待つ**設計なので、
最悪 1 脚 4 秒・8 本。20 口座 40 脚なら最悪 160 秒・320 本。押し込みならこの待ちも消える。

**既定は `sendVerification=false`。** 有効になるのは (1) 契約が true、(2) 出所層が LIVE、
(3) その口座が VERIFIED かつ鮮度内、の三つが揃ったときだけ。どれか欠ければ REST へ落ちる。

| 0 | `python broker_gateway.py --probe 45` | 注文を送らない。VERIFIED まで何秒か | 何もしない |

(差分ログに何も出ないことを、実際に建玉があった周期で確かめるため)。

**いまどの段まで進めるかは `python verify_r118_live.py` が出す**(読むだけ・通信なし)。

### 既存注文の引き継ぎ

**何もしなくてよい。** 根拠:

* Gateway は接続時に `Tv_ListPositions` / `Tv_ListOrders` で**全口座の現状**を取る。
  切替の瞬間に建玉や注文があっても、そのまま状態に入る。
* 所有権の束縛(`orderId` / `receipt`)は**凍結プランの台帳**が正本で、出所では決まらない。
* REST と Gateway で**注文行の 14 欄が 1 つも違わない**ことを試験で固定した
  (`receipt` は両経路とも `derived_receipt(platform, account, orderId)` から出るので同値)。
  OCO 兄弟の判定(R80)も両経路で一致する。
* **建玉の `position_identity` も両経路で一致する**ことを試験で固定した。これは
  `account` / `accountId` / `symbol` / `side` / `orderId` / `receipt` / `filledAt` の
  hash なので、1 欄でも違うと**切替の瞬間に同じ建玉が別物に見え**、世代が付け替わって
  所有権が切れる。危なかったのは口座欄で —— **一覧の行は数値の `accountId`、REST は
  口座名**を返す(2026-09-19 に実ブローカーで確認)。Gateway 経路でも口座名に揃えてある。

つまり **切替の前後で同じ注文が同じ identity として読める**。保有中に切り替えても
管理は途切れない。ただし段 4(送信検証)と段 5(Coordinator)は**送信の形が変わる**ので FLAT のときに。

### 戻し方(緊急)

```bash
# 観測だけ戻す(即時・プロセスを止めなくてよい)
NQX_GATEWAY_MODE=OFF

# 送信の並行化だけ戻す
NQX_COORDINATOR_LANES=1
NQX_COORDINATOR=0

# 常駐を止める
# → .secrets/broker_gateway.lock の pid を止める
```

環境変数は契約より強い。**契約ファイルを編集できない状況でも止められる**ようにしてある。
既存コードは 1 行も削っていないので、OFF に戻せば R117 以前と完全に同じ経路になる。

### 12C. 常駐の自動起動(契約 `gateway.autostart`、**既定 false**)

§7 で「自動化するなら契約のスイッチを足してから」と書いた部分を実装した。
`nqx_cycle` が毎周期 `broker_gateway.supervise()` を呼び、

* `mode == OFF` なら**何もしない**(観測に使っていないのに常駐させる意味が無い)
* `autostart != true` なら生死を出すだけ(**既定はこちら**)
* 常駐が生きていれば触らない / ロックを持つプロセスが居る間(heartbeat 2 分以内)も触らない
* 3 回続けて heartbeat が出なければ 1 時間止めて `.secrets/broker_gateway.log` を見てもらう

既定を false にしてあるのは、**接続が CrossTrade の利用者あたり 1 本**だから ——
人が手で張った接続を周期が勝手に切ると、切られた側は気づかない。
緊急停止は `NQX_GATEWAY_AUTOSTART=0`(契約より強い)。

**手で起動・停止するとき**(監視ループが止まっている間はこちら):

```bash
NQX_GATEWAY=1 python broker_gateway.py --start   # 切り離して常駐(注文は送らない)
python broker_gateway.py --status                # ALIVE / STALE と pid
python broker_gateway.py --stop                  # heartbeat の pid を止める
```

`--serve` は前面で回るので端末を閉じると止まる。`--stop` は **heartbeat が
5 分以上古ければ止めない** —— pid は使い回されるので、古い pid をそのまま殺すと
無関係のプロセスを落とす。
